# Ego REL summary synthesis and verification

Parent index: [Planning](./INDEX.md)

## Purpose

Freeze the tested two-call contract for turning a consolidated REL topic and its supporting Memories into verified Ego summary points. The summary gives current project context and retains exact source references for the details it carries.

## Overview

**Status:** Accepted design for the REL-backed summary. The existing audit hands off a suggested topic and exact Fresh Memory references. [Audit handoff](memory-web-audit-handoff-spec-2026-11-26.md)

The normal sequence is **Audit → Consolidate and compare → Synthesize → Verify → Publish**. Synthesize combines the earlier Summary Extraction and Summary Creation steps in one structured request. Verify reads the exact resulting points and their source packet in a separate structured request. One topic that reaches both stages takes two text-generation calls. Audit discovery and topic embeddings have their own costs. [Earlier Ego design](https://github.com/Lokee86/Reliquary/blob/2b5bd0ea/docs/ego-web-synthesis-plan.md)

## Ownership and sequence

1. **Accept and save the audit handoff.** Application uses the existing authorized Fresh Memory recheck and saves the topic and exact references for the active PHY, source REL and source cut before acknowledging Ego work. Use the existing [durable handoff design](roadmap.md#ego-audit-handoff-and-recovery) for restart and cleanup.
2. **Consolidate topic proposals and compare with saved sections.** Ego embeds topic text and begins with the agreed similarity threshold of 0.85. Fold distinct source references into the retained candidate before dropping a duplicate proposal. Compare the retained candidate with existing sections for that source REL. Skip synthesis when a matched section has no new exact Memory revisions. Bind the matched section identity and the new references to the work. The topic or match score guides selection and contributes no evidence.
3. **Synthesize the topic once.** Ego prepares the authorized Memory packet and asks for up to five independently readable points with explicit status, time scope and source quotes. For a matched section, retain the exact set of new source revisions alongside the work. Ego validates the reply and assigns request-local point IDs. Use the captured slot table to bind each quote to a unique range in the authorized Memory. Each point needs at least one exact citation. Repeated slot-and-quote pairs, unknown slots, empty quotes and ambiguous matches fail the point's citation check.
4. **Verify once per topic.** Submit the frozen points with their IDs and the same Memory packet to the verifier. Each point has independent meaning, status, time-scope and attribution judgments. Keep only points with valid citations and all four judgments supported. A hold affects that point. A valid response with zero accepted points completes the attempt without new summary content. Rejected points have no automatic rewrite, relabel or third call. An incomplete or malformed stage reply follows the saved work's retry handling and does not count as a completed topic.
5. **Publish verified points and advance the source cut.** Ego proposes the section update. For a matched section, carry forward eligible unaffected points and add verified points that cite at least one of the new Memory revisions. Apply existing source standing, suppression and append-only revision rules. Application rechecks authorized owner bindings and exact source standing before owner-session publishes the resulting summary and source cut to the active PHY. Release the run's work rows after that commit. A source change during inference requires revalidating the work against its new capture before reusing any output. [Summary contracts and controls](roadmap.md#ego-summary-contracts)

Keep synthesis, verification and the point acceptance policy in `reliquary-ego`. Application orchestrates source access, configured inference and publication through the existing owner boundaries. Switchboard supplies structured inference and embeddings through the configured routes. The accepted sequence uses separate structured requests and can bind the same model for both. The trial used GPT-5.6 Sol at low reasoning effort in both calls. The PHY preference summary, Personality, and later context selection have separate contracts. ## Request and result contract

| Stage | Request | Structured result |
| --- | --- | --- |
| Synthesize | `topic`, captured `as_of`, and `memories` with opaque request-local `slot`, `source_date`, and authorized `text`. | `points` contains zero to five items. Each has `statement`, `status`, `time_scope` and a `support` list of `{slot, quote}`. |
| Verify | The same `topic`, `as_of`, and `memories`. Add exact synthesized `points` with a caller-assigned `point_id` on each. | `checks` has exactly one result per submitted `point_id`. Each contains `meaning`, `status`, `time_scope`, `attribution` and `hold_reason`. |

The caller retains the mapping from a slot to its authorized source, revision, body and range. Source roles such as new versus already used are tracked by the caller. Check result structure and point IDs independently of the model judgments. Reject unknown, missing or duplicate result IDs. Each judgment is `supported`, `unsupported`, or `uncertain`. The verifier gives a short evidence-based reason for any hold and an empty reason when all dimensions pass. It returns judgments for the supplied text.

- **Meaning and attribution.** A point's full wording and named roles must be grounded by its cited Memories, including their authorized surrounding text. An uncited Memory can expose a conflict or correction. The title and summary system name supply no speaker or project identity. Use neutral wording when a name is ungrounded. Two dated states alone cannot establish the immediate predecessor of the later state.
- **Status.** Use `observed` for an established event or state, including a documented pending or under-review state. Use `planned` for a stated schedule or commitment, `requested` for the ask, preference or instruction itself, `possible` for a source-supported unresolved or contingent prospect, and `expected` for an explicit prediction.
- **Time scope.** Use `past`, `current`, `future`, or `unspecified`. Ground each date in the cited Memory for that clause. An explicit occurrence or effective date takes precedence over the report date. Use `as_of` to interpret labels. Keep earlier dated snapshots explicitly dated. The verifier can accept either past or current for a date-qualified latest snapshot of an explicitly continuing state with no newer change. A separate standing rule belongs in its own current point even when a source reports it beside a dated snapshot. An expired, lifted or superseded rule can be historical with its supported end date.
- **Selection and grouping.** The five-point cap limits entries. Choose useful facts for the title and combine clauses when their subject, condition, or timing forms one coherent point. Preserve each clause's scope and qualifiers. A passed verification result applies to the submitted point. It supplies no judgment on omitted evidence or coverage of the topic.

## Trial evidence and limits

The final topic pressure trial used eight authored packets with seven relevant facts each. The scored run used 16 live calls, cleared all 38 proposed points, and matched all 50 quotes to their selected source text. Manual comparison found 51 of 56 facts fully preserved. The initial two print packets had swapped inputs. Their four calls were excluded after those two packets were corrected and rerun.

The misses were the Riverside layover, a webinar comment thread closure, and the separate donation of 11 unclaimed coats where synthesis kept the shelter's receipt confirmation. Two print facts lost detail: the member scope of the orientation requirement and visitor passes' scanner permission. The verifier cleared the broadened print rule. Strong groupings included the start date, donation threshold and notice period of one clothing-swap appointment rule. Weaker groupings included staff maintenance permission with printer eligibility and caption prechecks with post-event archiving. The trial supports the accepted two-call design with a lossy point cap. Coverage, consolidation accuracy in a live REL, publication and provider performance remain implementation validation surfaces.

Earlier held-out temporal checks kept ongoing rules separate from snapshots and preserved the actual end dates of ended rules. The verifier flagged the original combined battery draft and rejected a completed shuttle rule labeled current. This evidence concerns the tested prompts on synthetic Memories.

Ordinary verification contains the draft points only.

### Tested synthesis prompt

```text
Write concise, independently readable Ego summary points for the supplied consolidated topic. Treat the listed synthetic Memory texts as the complete evidence. Keep distinct applicable scopes, conditions, status, effective dates and explicit time limits in the statements. Preserve what remains unresolved. A request, condition, expectation or rehearsal does not establish a completed outcome. Respect explicit corrections and scoped exceptions. Share evidence across a point only when it supports the complete wording. Omit irrelevant material and unsupported expansions. Return at most five points, each with status, time_scope relative to the supplied as_of date, and one or more source slots with short exact contiguous quotes from those sources. Choose observed for an established report/fact/state, planned for a stated scheduled or committed action, requested for an ask/preference/instruction, possible for unresolved or contingent prospects, expected for an explicit prediction. Split mixed statuses if needed. Judge status by what the point actually asserts. A documented review or decision state is observed even when the outcome is unknown. If a source says a request remained under review, preserve that known state with its date or scope. When the point reports what someone asked for, use requested. Use possible only when the point states a source-supported outcome that may occur or remains contingent. A pending review by itself does not make any outcome a supported possibility.
Use the topic title to find the subject. The title and generated topic text supply no evidence and cannot identify a person, speaker, project, or other entity. Use a name only when its presence and its connection to the stated event, role, preference, or project are supported by a cited Memory's text or explicit source metadata. A name present elsewhere is insufficient to establish that connection. For first-person text with an unnamed speaker, express the preference, instruction, or event in neutral wording with the supported scope. Do not invent a speaker, identity, or personal pronoun. If only the topic title supplies the project name, use the descriptive label supported by the source and preserve distinctions such as different environments, actions, or teams. Preserve the useful claim when the name can be omitted without changing its meaning. Keep names the source does identify. Two dated states alone do not establish that one immediately replaced the other. If keeping both, express them separately without asserting an unsupported transition.
Time scope: Give each point one main temporal claim. When a dated past action or milestone and an ongoing restriction or condition each convey useful facts, write two separate points with their own citations and labels. Keep an earlier completed action in past, an applicable ongoing rule in current, and a prospective action or target in future. Preserve the effective date of a continuing condition when it is a qualifier of that condition rather than a separate event. Report a state known from a dated check or report with its exact date in the statement. Ground each explicit date in a cited Memory that directly supports that specific claim or clause. Use the source's stated event or effective date for an event or rule. Use a report's source_date to date a snapshot only when that Memory actually reports the state on that date, and honor any different explicit date for the state in its text. If a rule is still in effect according to a dated Memory, describe it as confirmed on that Memory's supported date. Never move a confirmation to as_of or to the date of a later Memory about a different fact. The audit as_of date is a reference for the time_scope label and provides no factual evidence. If no date is supported for a clause, preserve the claim without adding a date. When the statement is bounded to a snapshot before as_of, default to past even if the source said the state was still in effect that day. For a snapshot of a continuing state on as_of, use current. Keep clearly ongoing rules (such as terms of an active program) in current. If a dated snapshot such as a delivery or inventory update appears alongside a separate standing obligation, write distinct points even when both facts were reported together or could grammatically share an as-of date. Preserve the dated observation as past and the standing obligation as its own current point, including any end condition the source specifies. A recurring or condition-bound obligation that the sources say continues stays current unless the evidence shows it ended, was replaced, or only applied historically. Do not fold the obligation into a past snapshot by moving an as-of date in front of both clauses. Do not project a dated snapshot beyond its date.
Return the structured response directly. Use no tools.
```

### Tested verification prompt

```text
Independently verify each proposed Ego summary point against the supplied Memories. Give one check per point ID. Judge the four dimensions separately. Do not rewrite the points or choose a preferred label when the supplied label is defensible. If regression_controls are also supplied, check those point IDs independently using exactly the same criteria. Neither the proposed points nor the controls are evidence for any other point.

Meaning: Check the complete claim, including entity, scope, condition, and chronology. Surrounding text in a cited Memory can support its quote. An uncited Memory can reveal a conflict or correction, but cannot supply missing support. A documented earlier state does not establish the immediate predecessor of a later state. Keep conditions, uncertainty, and limits stated by the sources. Evaluate speaker and project grounding in the attribution dimension.

Status: Judge the principal assertion by what the sources actually establish.
- observed: a reported event, established fact, or applicable state.
- planned: a stated schedule or committed action. A planned action need not have happened. A target can be planned if described as scheduled or as a stated plan.
- requested: an ask, preference, or instruction. A request remains a request when it is pending, unapproved, or concerns a future action.
- possible: an unresolved or contingent prospect, including conflicting tentative dates awaiting resolution. A condition or unresolved status does not make the prospect a confirmed plan.
- expected: an explicit prediction. Distinguish it from a request or mere possibility.
A condition, lack of approval, or other context can qualify the main assertion without changing its status. Still reject wording or a label that turns a request, expectation, or contingency into a confirmed plan or outcome.

Time scope: Use as_of and the time of the substantive assertion. Apply the dated snapshot rule below before deciding that a date anchor makes a label wrong.
- past: a completed event, historical condition, or snapshot explicitly bounded to a date before as_of.
- current: an ongoing condition, applicable instruction, open request, or unresolved state.
- future: an upcoming action, target, or unresolved prospective event, including when its uncertainty is known now.
- unspecified: no meaningful time scope is established.
Dated snapshot rule: If the statement retains the date of a previously reported state and its wording is bounded to that date, accept past for a valid earlier snapshot. Also accept current for that same date-qualified wording when it reports the latest known state, the cited source explicitly describes the state as continuing or still open at that date, and no newer source changes it. In this case both labels are supported: past describes the dated report and current describes the latest known continuing state as explicitly dated in the statement. Keep the date limit when applying this allowance. A date alone does not make a continuing state label unsupported. Do not extend the allowance to a bare claim about today, a superseded or explicitly ended state, a one-off snapshot without indication of continuation, or a completed event. A dated snapshot of a continuing state on as_of supports current.
Completed events and ongoing rules: A separately asserted completed event and an ongoing restriction belong in separate points. Reject labeling a point past if it asserts an ongoing restriction as a separate fact. Also mark time_scope unsupported when past covers both a dated observation and an independent standing obligation that the cited sources say continues. Apply this even if the whole statement opens with as of an earlier date, uses past tense for the obligation, or quotes both clauses from one Memory. A recurring or condition-bound obligation remains an independent current claim when its end condition has not been reported met and the source says the rule continues. Judge the source's scope rather than treating the shared date as permission to historicize the rule. A genuinely historical or ended obligation can be past. A standalone dated report of a state without a separate continuing obligation remains subject to the dated snapshot rule. An effective or start date can qualify a single ongoing rule when no independent past event is asserted. A resolved, completed event does not become current just because it is the latest described event. For a supported statement about an open request or unresolved status and its scheduled or prospective outcome, accept current or future when the wording preserves both the open status and upcoming timing.

Attribution: Check each person, speaker, author, actor, owner, project, team, or other named entity and that name's connection to the stated fact. Only cited Memory text and explicit source metadata can establish the connection. A topic title, summary system name, or occurrence of a name in an unrelated role or another Memory cannot establish it. First-person text does not identify its speaker unless a cited Memory or source metadata explicitly makes the connection. A descriptive, neutral statement can be supported with an unnamed speaker or project. Accept grounded names in the roles the sources establish. Mark invented or wrongly attached names unsupported even when you agree with the rest of the claim. Assign name grounding to attribution and judge other meaning separately.

Use supported when the specific dimension is defensible, unsupported when the source contradicts it or the point adds an ungrounded claim or name, and uncertain when the cited material genuinely leaves the dimension ambiguous. Set hold_reason to a short evidence-based explanation when any check is uncertain or unsupported, or an empty string when all are supported. Return the structured checks directly. Use no tools.
```
