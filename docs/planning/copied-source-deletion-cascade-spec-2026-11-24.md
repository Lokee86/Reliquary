# Copied-source deletion cascade

Parent index: [Planning](./INDEX.md)

## Purpose

Make a committed chat deletion or rewind remove access to the affected copied content and knowledge everywhere Reliquary serves it. Hermes and Mercury report what their transcript authorities committed. Reliquary owns the durable tombstone and applies its effects consistently to Archive, Memory, and Observation reads. Archiving or restoring a chat leaves its copied knowledge available.

## Overview

Both adapters already report whole-chat terminal changes through the copied-source path. Core writes an Archive conversation tombstone. Memory retrieval and Observation standing can still admit derived content, so the hosts compensate with their own source checks. Hermes has a committed rewind operation, but its memory callback supplies only a rewind flag. Mercury's native Gateway has no committed rewind mutation at the current integration pin. The cascade extends the existing copied-source boundary and makes committed rewind reporting part of the host work. ## Source change contract

| Host change | Reliquary effect |
| --- | --- |
| Archive or restore a chat | Keep the current copy, its knowledge, and the source binding. Restore can continue normal capture from the retained head. Delete after archive still takes the ordinary delete path. |
| Delete a chat | Permanently tombstone the authenticated copied conversation, including accepted extensions, and retire its sourced content. Reuse the existing conversation tombstone. Scope lineage and bulk deletes to the actual affected conversation IDs committed by the host. |
| Commit a rewind | Retract just the removed suffix of the copied conversation. Keep the surviving prefix and active copies in other branches. Resume capture at the last surviving message or the empty start of the chat. |

Use one authorized Root operation for copied-source changes. Bind each notice to a stable host event ID and the authenticated source scope and accepted owner receipt. For whole-chat deletion, an accepted receipt for that logical copy still identifies the target after a concurrent extension. For rewind, require the exact accepted pre-change head and last surviving stable message, or an empty prefix. Resolve the affected copied suffix from the accepted receipts and validate it against the committed host change. Use a bounded anchor-and-head representation when the suffix is large. When the host has changes the REL has never accepted, reconcile only the intersection proved by that same committed event. The identity is the durable host message ID. A text match, physical row number, or truncated provider view supplies no removal authority. [Append and receipt checks](../../crates/reliquary-application/src/native_import_workflow/source_hermes_extension.rs) · [Public copied-source API](../public-product-api.md#native-and-copied-source-import-contracts)

The accepted receipt selects the destination REL even after a host switches the active REL or changes project routing. Apply the operation independently to any other authorized REL that has its own accepted receipt for the reported removal. Existing copy scope and grants still apply. The current adapters copy to RELs. A shared message ID, wording, or Entity identity gives no authority over another branch, an unrelated REL, or a PHY.

## Core publication and cascade

- Reuse the native conversation tombstone for whole deletion. Add a versioned owner record for rewind that seals the removed range, the surviving anchor, and the resulting source head. Validate authorization, owner generation, accepted source and current head before publication. Persist the source change and its receipt at one owner cut. Exact retries return the same receipt. Conflicting event reuse and stale rewind heads fail without partial effects. An already deleted source stays terminal when an earlier rewind or snapshot arrives late. A committed tombstone fences queued imports, append attempts rooted in a removed head, and reuse of removed message IDs within the same copy. A new suffix starts at the surviving head with fresh message IDs.
- Make the owner session the authority for effective source eligibility. As soon as the tombstone is durable, all affected content becomes unavailable at the same cut. Resolve the cascade from exact stored provenance, including content, grounding, and episode spans where extraction used broader context. A Memory whose proof relies on removed source is effectively tombstoned. Entirely surviving Memories stay available. Use the existing accepted receipts, provenance and dependency lookups. Any derived cleanup may run later because every reader sees the effective tombstone immediately.
- Apply the same eligibility to Archive and Echo ranges and issued references, lexical and vector candidates, Memory inspection and history payloads, and graph traversal. Skip any indexed passage that overlaps removed text until the next index update can represent its surviving content. Keep its removed segments out of returned text and ranking. Exclude affected Memory nodes and evidence derived through them from graph and Entity or Relationship views. Keep independent Entity evidence, valid edges and manual facts usable. Refresh derived Community views affected by the change before serving their cached claims or labels. Use the same eligibility for Ego and Perception audit inputs and other background processing.
- Remove affected Observation revisions and their dependent chains from current reads as soon as their support becomes ineligible. Use existing ChangedSupport and UpstreamReview handling, and include source authority changes in the Perception work and publication cuts. Reuse the existing Verify contract when surviving evidence could support the claim. Publish a verified successor with new citations if it stands on independent evidence, even when the wording stays the same. Withdraw a claim without eligible proof. Immediate removal from recall works without waiting for a model. [Observation standing](../../crates/reliquary-owner-session/src/session/observations.rs) · [Reconsideration](observation-reconsideration-spec-2026-11-24.md)
- Bind retrieval, inspection and in-flight work to the source eligibility cut. Recheck that cut before disclosure, delivery recovery that would expose a body, and publication from earlier evidence. Reject a stale prepared result without changing its selection. Durable receipts and tombstone metadata remain usable for exact retry and history accounting. A current tombstone governs content served through an old citation or confirmed manifest. Validate older publications against the source cut at which they were written. Restore the removal state through full replay and verified checkpoint suffix replay, and keep it through verified copies. Refuse maintenance that would lose the removal proof. ## Host reporting and retry

- **Hermes.** Reuse the source observer and durable outbox for committed delete and bulk delete. Stop enqueuing terminal work for archive. Extend the generic host lifecycle boundary to expose replayable committed transcript-removal receipts. Project stable message IDs and the surviving anchor from the canonical rewind transaction, including the CLI and Gateway paths. A rewind flag, session switch, and provider snapshot remain separate inputs. Verify the reporting capability at the exact supported Hermes pin. Follow the existing scope and signed host-inference and source protocols. [Hermes source protocol](https://github.com/Lokee86/reliquary-hermes/blob/662a8763ab935a7a13e57ad0669e7a0b01380e76/docs/protocol.md)
- **Mercury.** Reuse committed catalog deletion and the native memory reconciliation path. Separate normal archive and unarchive from the terminal source marker and from inference based on the active session list. Add the smallest authenticated committed rewind path needed at Mercury's native session authority and connect a normal native entry point to it. Persist the surviving anchor and exact removed logical message IDs with the authority change. Wire that receipt through the native Reliquary adapter. Full desktop and slash-command parity is separate work. [Mercury deletion and archive](https://github.com/Lokee86/hermes-rust-rewrite/blob/406baebb909eff1a1024c1fb98c4cde66f410165/crates/gateway/src/catalog.rs) · [Source reconciliation](https://github.com/Lokee86/hermes-rust-rewrite/blob/406baebb909eff1a1024c1fb98c4cde66f410165/crates/plugins/reliquary/src/memory.rs)
- In both hosts, tie the durable removal intent to the transcript commit or a replayable committed receipt, so restarting between host commit and delivery cannot lose the notice. Replay changes in committed order for the same source. Keep each notice queued until every bound REL acknowledges the Core cut. Reuse the existing adapter fences while a removal is known and still syncing. They prevent stale handoff and further publication from the affected source during the gap, including when Core is busy with an import or the owner is unavailable. Recovery resumes at the existing owner writer boundary and retries the same intent. Expose pending sync as an operation state. Once Core acknowledges the change, both hosts use Core's visibility decision and retire the per-hit lifecycle veto. Keep their session and authenticated delivery checks.

## Compatibility and migration

Existing REL 2.1 files open with their original headers, owner IDs and receipts. An old committed whole-conversation tombstone remains terminal. Older writers could record archive and delete through the same terminal operation. Preserve those committed tombstones and apply the shared visibility rule to them. Archived chats with a live copy stay available. During host queue migration, retire an uncommitted archive-only intent and replay a confirmed deletion. Recover ambiguous notices from the authority's committed evidence. A current archive flag alone authorizes no tombstone.

Move both adapters directly to the same Root contract. Keep the documented whole-copy tombstone API backed by it for existing consumers. Version the new rewind record and require a reader that can enforce it once a REL contains one. Match each host adapter to its supporting Core and host authority revision at rollout. Existing applications may continue using older builds with their separate owner files. Prove compatibility on disposable copies before switching any installed profile.

## Implementation plan and focused tests

| Step | Depends on | Deliverable and completion check |
| --- | --- | --- |
| 1. Publish source changes in Core | Existing copied-source receipts and owner writer | Extend the existing copied-source test with whole delete and exact suffix rewind. Reopen a pre-change REL and a REL with a recorded removal. Prove retry, scope and head checks, a stale append refused, a new suffix at the surviving anchor, and a second independently copied chat unchanged. |
| 2. Enforce the cascade in Core | Step 1 | Extend one mounted retrieval and review fixture with exact source dependencies. A deletion and a rewind hide the affected Archive and Echo range, overlapping indexed passage, Memories and dependent Observations before any model reply. Verify that inspection and a prepared or retained return cannot expose removed content, and that an affected node cannot seed traversal or supply audit evidence. Check the surviving prefix, unrelated facts, an independently reverified successor, and persistence through reopen. |
| 3. Report committed changes from each host | Step 1 for integration, step 2 before removing the host veto | In parallel, wire the Hermes receipt and outbox and Mercury authority mutation and reconciliation. Each host runs one focused native fixture on a disposable REL through archive, rewind, continued capture, and whole-chat delete. Assert archive leaves recall available, the committed removals reach Core, and a withheld acknowledgment followed by restart retries to the same durable result. Verify the actual committed host receipt for rewind on each supported host. |
| 4. Verify and cut over together | Steps 2 and 3 | Run the targeted Core and host fixtures and the affected repository checks. Audit remaining host callers of the old lifecycle veto and archive terminal paths. Record exact tested pins, update the owning API, persistence and host docs, and keep the ongoing processing checkout and owner data outside the work. |

Use the existing copied-source external consumer, Gateway Observation retrieval, signed Hermes, and native Mercury WebSocket fixtures. Script any required observation verification locally. The completion gate is agreement between direct REL reads and both host recall paths at the acknowledged source cut. Upstream approval and catalog adoption are separate from test acceptance on the implementation branches.
