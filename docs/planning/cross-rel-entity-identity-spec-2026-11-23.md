# First cross-REL Entity identity comparison

Parent index: [Planning](./INDEX.md)

## Purpose

Let an authorized caller ask whether two existing Entities in different RELs refer to the same thing. Each answer must say what supported it and be reconsidered when that support changes. For example, two records for Alex Chen might independently identify Alex as the signatory for the same named contract. A shared name and the job title “engineer” leave the question open.

## Overview

2.1 resolves a Memory mention against Entities in one owner. Its reconciliation helpers propose local candidates and guard a local merge proposal. Neither path records a decision about two owner-qualified Entities. The original roadmap called for a relational comparison, an evidence receipt and repair when the evidence changes. This specification covers those three behaviors for a pair selected by the caller. [Original semantic sequence](https://github.com/Lokee86/Reliquary/blob/c6010fd30dd52acb81c667f7aed99b831307e49f/docs/roadmap.md#semantic-sequence) · [Current Entity resolver](../../crates/reliquary-entity-resolution/src/lib.rs)

## Operations and authority

- **Compare** starts from the recording REL, A. The caller supplies its local Entity ID and the peer pair (REL B, Entity ID). The key preserves that order and qualifies both IDs by owner. Equal Entity ID bytes in different RELs are valid. A requires an active Instance with `ManageRel(A)` and a writable mount. B requires a separate REL read grant and may be mounted read-only. Grants precede lookups. Dependencies, paths and knowledge of either ID confer no access.
- **Inspect** returns the latest outcome and its freshness, or a requested earlier receipt for this specific pair. It requires current read access to both RELs. Recheck access before returning hydrated evidence. If the pair has never been compared, the result is empty. If inputs changed, the latest receipt is historical and the current state is pending reconsideration. Inspection never invokes the evaluator or publishes. Missing authorization or an unavailable peer yields an access or availability error without disclosing comparison details.
- **Revisit** uses the same comparison operation and write grants. A managed worker can resume the pairs already recorded in A for which the active Instance has peer access. Either owner can serve as A when explicitly selected. Recording on A never writes B or establishes a reciprocal receipt. The decision concerns only this pair. Both Entities keep their IDs, aliases and graph edges. A future consumer must look up each pair it relies on.

Accept two distinct REL owners and active, non-principal Entity endpoints. Reject an invalid first request before evaluation. If an endpoint later retires or becomes ineligible, expose the old decision only as history and report the pair as unavailable for a current decision. A missing grant takes precedence over that status. PHY data, automatic candidate discovery, corpus calibration and Observation synthesis belong to later work. [Historical owner and privacy decision](https://github.com/Lokee86/Reliquary/blob/c6010fd30dd52acb81c667f7aed99b831307e49f/docs/decisions/0034-cross-owner-relationship-graph-and-active-phy-privacy.md)

## What counts as evidence

1. Capture each endpoint's current revision, kind, name and aliases. Look up its active local Relationships by participant. An eligible Relationship names this endpoint and another active local, non-principal Entity, and cites a current active local Memory. Exclude a Relationship that requires foreign participants or evidence, without following or returning those references. This keeps a comparison of A and B from silently including a third owner.
2. Use the existing Relationship kind, participant roles and source quote. At creation Core checked the original Memory revision, body, field and span. Of those grounding details, the Relationship retained its Memory reference and quote. Locate the quote exactly once across the current title and content, on UTF-8 boundaries. Record the **observed** Memory revision, body ID, field and byte range. A missing, repeated or pruned quote supplies no witness. If supported by multiple cited Memories, ground each witness separately. Recheck direct source provenance and verify the cited quote names the participants. Treat two citations with the same known source lineage as one corroborating source. [Relationship creation](../../crates/reliquary-owner-session/src/session/perception_lifecycle/relationship.rs) · [Stored fields](../../crates/reliquary-perception-store/src/relationship_model.rs)
3. Order evidence by owner-qualified Relationship and Memory IDs. Supply at most four incident local Relationships per side and keep the combined evaluator input within the existing 16 KiB Entity budget. An overflow returns `Unresolved / evidence_limit`. Never confirm a match from a truncated selection. The receipt identifies the limit reached and the bounded frontier. Fingerprint the canonical bounded inputs together with their references. Include each endpoint's supplied fields, the considered Relationships and participants with revisions, cited Memory revisions/body IDs, verified spans and relevant exclusion or limit markers. A peer remounted with different content at the same revision must change the fingerprint. Reconstruct historical evidence only when the retained material matches the receipt.
4. Apply the existing Entity resolution route to a pair-specific structured judgment. A `SameIdentity` judgment must cite independently grounded witnesses on **both** sides that corroborate a distinguishing fact about the endpoints. It also requires compatible kinds and no unresolved contradictory evidence. `RelatedDistinct` also requires affirmative two-sided evidence that distinguishes the referents. Otherwise record `Unresolved` with a bounded reason such as insufficient evidence, ambiguity or conflict. Equal names, aliases, numerical similarity and generic roles cannot establish identity. Validate that citations point into the supplied evidence. Missing two-sided support can be recorded without a provider call. If storage or the provider fails, or the response is invalid, leave the operation retryable without appending a judgment.

## Receipt and reconsideration

Publish one versioned receipt in A per changed decision input. Store the directional key, revision and predecessor, input fingerprint, policy version and nonsecret route identity (or the deterministic rule used), outcome, reason code and indexed evidence references for each side. Capture the exact basis for an unresolved decision too. Keep peer prose, quotes, prompts, credentials and free-form model reasoning out of durable receipts and diagnostics. The holder of A's file can see the recorded link and references. Hosted reads and any hydration of retained evidence require both grants, including history views. Pruned evidence is reported as unavailable without recreating it from the receipt.

A second compare on the same current evidence and bound policy returns the same receipt. When support changes, append a successor even if the verdict is identical or an earlier fingerprint recurs. An old positive immediately loses current standing on an authorized read of changed evidence. Revisions form one chain per directional key. Reopen reconstructs it from A alone. During processing, keep the route bound for the attempt and its retry. An explicit change of comparison policy or bound route requires a new evaluation. Verification of B's *current* state is a separate authorized operation.

While comparison processing for A is active, use the existing owner-worker lifecycle to check registered pairs in bounded batches. Use owner cuts and mount identity as cheap change hints. Recapture only the named pair's evidence and compare the fingerprint before invoking the evaluator. A newly added Relationship counts, even if the previous receipt had no witnesses. Retirement, source replacement, pruning and remount also invalidate affected inputs. Unrelated writes and the comparison's own receipt must not trigger judgment or append. Resume starts with a fresh authorized check, covering missed updates and incomplete work across restart. Processing stores no credentials. Merely opening a REL starts no comparison work.

Prepare snapshots under grants, evaluate outside both owner locks, then revalidate credentials, both mounts, exact inputs and the expected predecessor at publication. Hold the topology fence and acquire mutable mount guards in owner-ID order for this last check and A's durable append. Immutable peer mounts need only a stable mounted session. Use cheap revision checks under the guards for already captured bodies. If a cut advanced, recapture outside the guards and reuse the judgment only when its full input still matches. A concurrent winner on identical inputs satisfies a retry. A stale result, revoked credential or interrupted append can never become a second current decision.

## Storage and compatibility

Use a REL-only typed record in the clocked publication envelope. Full replay checks the recording owner, retained local revision references at the publication cut and the revision chain, and structurally validates foreign references without opening B. A later prune does not invalidate a historical receipt or require recovering its old quote. Existing native 2.1 RELs begin with an empty history. Preserve owner IDs and headers. Include comparison state in the private checkpoint and historical proof. A same-owner verified copy, prefix extension, description pruning and storage reclamation must preserve the receipt chain. Reject fresh-history rewrites and divergent reconciliation involving receipts before publishing a destination until those workflows can preserve the chain. Standalone opening, backup and recovery require no peer grant. [Owner session](../architecture/owner-session.md) · [Storage](../architecture/storage.md)

## Notes

This is a proposed Core contract. Ordinary owner-local mention resolution and local Observation evidence can proceed independently. Cross-REL Observation consumers may use a current authorized comparison when their proposition actually depends on the two Entities sharing an identity.
