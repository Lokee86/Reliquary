# Shared Memory Web audit and first Perception Observations

Parent index: [Planning](./INDEX.md)

The [audit handoff follow-up](memory-web-audit-handoff-spec-2026-11-26.md) defines the next revision of the Ego and Perception proposal contracts.

## Purpose

Give Ego and Perception one way to audit an authorized Memory Web with predictable coverage and cost. Ego uses it to extract grounded material for summaries. Perception uses it to discover and verify Observation candidates, including Relationships between Entities. Core already resolves mentions and finds Memories and Relationships by Entity. It currently lacks the audit controller and a product path that turns those inputs into Observations. [Current semantic processing](../architecture/semantic-processing.md) · [Historical Ego audit](https://github.com/Lokee86/Reliquary/blob/2b5bd0eabfbac0a85f899d7d730220b5e8e93efa/docs/ego-service-crate-extraction-spec-2026-10-28.md#L55-L77)

## Overview

Application captures one authorized REL cut and supplies a bounded first working set or the changed work for a recurring audit. Each batch makes one structured discovery call that returns two independently validated lists. Ego receives candidate subjects and their Fresh evidence. Perception receives candidate propositions and their eligible evidence, including Stale and Dormant Memories when sampled. The audit ends with those candidate lists. Perception hands its proposals to the creation workflow. Ego passes validated subjects and supporting excerpts to later summary generation. [Observation creation](observation-creation-spec-2026-11-24.md)

## Ownership and scope

| Owner | Contract |
| --- | --- |
| New internal audit crate, `reliquary-memory-audit` | Plan bounded batches from an ordered, supplied working set, track mandatory exposure by feature, run the combined structured extraction, allow bounded evidence requests, and bind results to Core-issued source references. |
| Ego semantic crate | Select its Fresh working set and own the subject and evidence fields of the combined response. Prepare typed, source-linked inputs for later summary generation. |
| Perception semantic crate | Select routine and older Memory inputs. Own the ordinary or relational candidate fields of the combined response and the downstream creation contract. |
| Gateway, Application and owner-session | Gateway supplies current grants, a stable mount and scheduling. Application composes the shared audit and domain contracts using a configured endpoint. Owner-session prepares exact, read-only facts and publishes accepted Perception work through the owning store and native commit boundary. |

Both semantic crates depend on the auditor and Application depends on those semantic crates. The auditor accepts immutable batch values and an authorized lookup callback. Perception supplies its own typed candidate context. Authorization, source selection policy, publication, and provider configuration stay with their existing owners. Use `ConfiguredRuntime::general_endpoint()` via Switchboard for the shared audit and extraction. Pin the nonsecret route and contract version for each attempt. An unavailable route leaves work pending, with a bounded retry delay for transient failures. Future specialized routes can bind through the same boundary. The release covers one authorized REL per audit. It delivers Ego audit/extraction and the complete same-REL Observation lifecycle, including ordinary and relational Observations, reconsideration, and verified Observation citations for higher Observations. Full Ego summary generation, PHY summary persistence, context injection, cross-owner synthesis, broader exploratory routing and production corpus calibration are follow-on work. Preserve owner-qualified references for later work. A future cross-REL route that relies on identity must use the authorized current effective decision, including operator-confirmed separation. ## Shared audit contract

- Application provides an ordered working set with eligibility for each list at a captured owner cut. Include the whole admitted set in one batch when it fits. Otherwise split it into deterministic batches. Give every admitted work item mandatory exposure for each list it serves before that part of the run completes. Bootstrap coverage applies to the selected page. Recurring coverage applies to the changed work and reserved Perception samples. Resolve references to exactly the captured revision. New writes can feed the next run. A withdrawn, replaced or unavailable required source invalidates the affected work. A permanently unavailable body is reported as excluded when planning the next working set.
- Each input identifies owner and history generation, Memory ID, revision and body ID, field and UTF-8 range. Give the model request-local source and participant slots. Bind those slots in Core. Count exposure only for slices actually sent as mandatory input on a successfully processed batch. Split oversized admitted bodies at UTF-8 boundaries and track their mandatory slices. Optional context and search results never satisfy mandatory exposure.
- A discovery response may request evidence relevant to its own task. Allow one optional follow-up round per combined batch, with at most two authorized lexical searches and four returned passages per query. Carry the requesting list's eligibility into discovery lookups. Offer Fresh results for Ego and include Stale or Dormant results for Perception when eligible. Restrict lookups to the same authorized source REL and the captured cut. Reuse indexed lexical candidates and hydrate only selected bodies. Recheck authorization and body identity before sending results. All reads are non-reinforcing.
- Pack up to 125 distinct Memories into each combined discovery request. Use the bound route's usable input budget, reserving space for instructions, provenance and output. Split at the Memory or route context limit, including when a single Memory needs several mandatory UTF-8 slices. Allow up to 8 KiB of optional passages within the route budget and a 16 KiB response, subject to lower endpoint limits. Allow up to four candidate items per list and verify at most four candidates per audit batch. Allow space for both lists within the response cap. Enforce the limits before provider dispatch or result acceptance. Track coverage and completion separately for the two lists. An unreadable response completes neither list. If one list is missing or malformed, retain a valid sibling list and retry the incomplete work against the same captured input. Reject individual items that fail evidence or contract validation. Bound each poll and continue from the last proven frontier. Keep private text and provider replies out of progress records and diagnostics. Adjust policy constants from observed workloads without changing the storage format.

## Working set and candidate extraction

Every passage carries its Freshness grade and the lists allowed to use it. A Fresh passage can serve both lists if it meets both sets of eligibility rules. Stale and Dormant passages serve Perception only. Core validates each citation for its own list after extraction, including citations to follow-up search results. An Ego candidate that cites an ineligible source is invalid. The summary generation stage receives only the validated Fresh evidence.

**Ego.** Apply Fresh-only eligibility to the selected work and optional context. When a cited source changes or leaves the Fresh set, pass the affected subject and exact evidence change to downstream Ego processing. Retain prior points whose provenance still qualifies. Revisit only affected points and recheck any remaining support under the current cut. An available source that becomes Fresh can enter the next recurring working set. Each candidate contains a subject and source entries with status and time scope. One source may support several distinct entries. The older whole-Web plan explains the original admission and coverage goals. [Historical Ego policy](https://github.com/Lokee86/Reliquary/blob/2b5bd0eabfbac0a85f899d7d730220b5e8e93efa/docs/ego-service-crate-extraction-spec-2026-10-28.md#L55-L77)

**Perception.** An invoked audit can read a Memory after Insomnia and Dream settle it. These conditions establish source readiness. Opening or inspecting a REL performs read-only work. Wait for required mention decisions to settle before relational discovery. Ordinary work can proceed while Entity evidence is pending. A later mention resolution or withdrawal makes the affected source eligible for relational work again. Use the same durable owner-local change frontier for new sources, source corrections and the parts of the graph affected by committed changes. Use current, readable, directly supported Memory revisions. Treat archived, retired, superseded and pruned sources according to their actual lifecycle. Stale and Dormant grades alone keep an otherwise eligible Memory in scope.

Perception's list uses the ordinary or relational contract selected for the batch. Each candidate carries one proposition, a status, a time scope and its exact source slots. Relationships also carry resolved participant slots. Both lists use the typed statuses `observed`, `planned`, `requested`, `possible` and `expected`. Time scope is `past`, `current`, `future` or `unspecified` as described by the source. Split propositions with different statuses into separate Perception candidates. Core checks eligible references and typed fields. Verification checks that the evidence actually supports the proposition and its qualifiers.

## Bounded first audit and recurring coverage

For an existing REL, freeze an initial authorized cut and cover its eligible, already-settled Memories in bounded pages. Publish accepted results as each batch completes. Keep the bootstrap cursor through reopen and continue until the initial cut is exhausted. The 125-Memory limit applies to each request. Between bootstrap pages, let ready recurring work advance independently from the initial cut. In a new REL, the first eligible group of 25 is the first working set. Opening or inspecting a REL remains read-only.

For a recurring audit, admit the due group of newly settled Memories and the affected sources from committed changes since the previous accepted frontier:

| Change | Work to revisit |
| --- | --- |
| Memory creation, correction, or eligibility change | The newly eligible or revised source and prior candidates that depend on its exact provenance. A retired, archived or unavailable source contributes an invalidation and its surviving eligible neighbors. |
| Added, removed or changed active Memory Graph relation used by the audit | Both affected endpoint Memories, using the recorded endpoints even when the edge is gone. |
| Changed Entity or mention resolution | The affected source and participant evidence for relational work, including old and new bindings where applicable. |
| A verified, current Observation is published or revised | Make its exact revision and eligible source lineage available as Perception evidence for affected graph regions. A derived Observation adds no credit toward the 25 newly settled Memories. A change to its standing also routes to dependent Observations. |
| Freshness crosses the Fresh eligibility boundary | For Ego, add newly eligible evidence or invalidate the affected prior source slots. Perception continues to use its separate eligibility and sampling policy. |

Pull bounded nearby context through existing direct links, resolved Entity lookups and authorized search. Local context can support a candidate without turning all adjacent Memories into mandatory work. A derived Leiden label, generation or index refresh creates no audit work by itself. Known invalidation of a published Observation's evidence follows the existing immediate review path. [Relationship candidate lookup](#relationship-candidates) · [Observation review triggers](observation-reconsideration-spec-2026-11-24.md#triggers-and-candidate-selection)

Use committed Memory, Graph and mention changes through a captured cut. Coalesce repeated work on the same identity to the latest eligible revision and retain invalidations for removed evidence. Track accepted work by list and advance its frontier only past accepted or deterministically excluded inputs. Resume bounded scans and incomplete exposure from durable state. Changes arriving during a run remain queued for a later cut. Keep bootstrap, recurring work and the older-sample positions independently resumable.

## Automatic audit cadence and sampling

Queue one automatic shared audit for each **25 newly settled source Memories** in the REL, including the first such group in a new REL. Count each eligible identity once, at first settlement. Revisions, explicit replacements of counted sources, retries, samples and derived Observation publication leave the count alone. Corrections follow their normal source and reconsideration paths. The existing REL's initial cut separates retained bootstrap history from the recurring count. Graph-only changes and source edits remain eligible for the next routine audit without incrementing the 25 count.

Use the owner-worker lease with one logical audit in flight per REL. Capture the due group and leave later eligible Memories queued for the next run. Persist accepted per-list coverage and unsettled work as batches commit. An accepted empty result can complete coverage. Interrupted work resumes from durable progress. Ordinary work can proceed while particular sources wait for relational mention decisions. Requeue newly eligible relational work without counting those Memories again.

Reserve **up to 15 Stale and five Dormant Memories per logical run**, in addition to the 25 new ones. Use eligible, readable revisions at the captured owner cut and current accepted-turn grades with same-turn events included. Rotate each band independently by stable Memory ID with wraparound. Visit at most 128 metadata rows per poll and continue sparse scans over further polls. Take up to the quota from each band and stop after one complete rotation if fewer are available. Avoid selecting the same Memory twice in a run. Omit unused slots. Persist sample positions and coverage so reopen resumes the unfinished run. Older samples belong solely to Perception. Ego continues its own Fresh working-set selection and mandatory exposure.

The new group and full older sample total 45 Memories. Changed endpoints and eligible context can enlarge the request. Pack the admitted working set within the 125-Memory and route context limits and continue any remainder in later requests for that run.

Submit each selected older passage for existing-Observation contribution as well as Perception discovery. Submit it even when discovery finds no new proposition. Record the handoff with sample progress once the passage has been covered and contribution work is queued or ruled out. The normal Perception worker handles that work independently of audit completion. Audit and rediscovery reads leave Freshness grades alone. ## Perception verification

Perception hands validated proposals to Synthesize, creates draft receptors, and checks the REL for additional evidence before verification. One native decision request checks the exact draft and its back-check hits. Synthesize handles changes to wording or citations. Finalize publishes only a cleared draft. [Observation creation](observation-creation-spec-2026-11-24.md)

## Relationship candidates

1. Start with the resolved Entity IDs on an admitted Memory. Reuse owner-session's Memory-to-Entity lookup, current resolved mention reverse lookup and active one-hop Memory Graph neighbors. The candidate context can include a second Entity in the same Memory or in a nearby linked Memory. Honor current mention decisions before falling back to supported typed retained decisions from migrated RELs. Participant and graph links select passages. The text establishes the proposition.
2. Deduplicate by owner-qualified participant set and evidence. Use active, distinct canonical Entities. Exclude generic, unresolved or retired endpoints. Bound the first pass to eight eligible neighboring Memories and four candidate contexts per anchor, deterministically ordered with same-Memory evidence first. Support multiple candidate Relationships involving the same participants. The candidate can carry up to four participants and optional role labels.
3. Use the current participant lookup to supply relevant manual or imported Relationships and prior relational Observations. Check a candidate against existing claims. Leave equivalent legacy claims in their original records. Their manual lifecycle remains available. The relational extraction contract returns a proposition, participant slots, optional roles and cited Memory slots. Co-occurrence, equal names or an existing ungrounded description alone leaves the candidate unpublished. The common verification path evaluates the claim and its evidence. ## Publication, reconsideration and compatibility

Publish both profiles through a single typed Observation history in the Perception store. Use a new versioned carrier in the existing native REL publication envelope. Persist the local owner/generation, stable Observation ID, revision and predecessor, active or withdrawn state, proposition, optional supported temporal scope, profile and participant roles, exact evidence references and lineage, and the bound policy/route and input fingerprint. Preserve supporting and contrary evidence references when they govern the decision. Store no provider prompts, source copies or private rationale. Publish the accepted results and Perception progress from one bounded completed batch in a single commit. A valid empty result can advance progress. Transport or validation failure cannot.

Authenticated Perception processing requires the existing writable REL and `ManageRel` boundary. Capture under authorization, perform inference outside the owner lock, and revalidate grant, mount, cited source/body/mention revisions and expected predecessor at commit. Unrelated writes can coexist. Identical accepted input retries return the prior result, including after a lost acknowledgement. A changed cited source or participant marks the existing head pending on read and triggers targeted reconsideration on the normal processing path. Successful reevaluation records reaffirmation of the same claim and exact support, publishes a successor on the same ID, or withdraws current standing when support has been refuted or lost. Transport failure leaves it pending. A later correction preserves history. Multiple legitimate claims about the same participants can coexist. Check duplicates by profile, normalized claim wording, participants and supported time scope. Route known equivalent drafts to the existing claim's contribution path and reuse its stable Observation ID. Inspect current and historical Observations through paged, grant-checked Root inspection. The reconsideration specification defines the contribution trigger, retrieval standing and same-REL derived evidence for this release. [Observation reconsideration](observation-reconsideration-spec-2026-11-24.md)

Native REL/PHY 2.1 files retain their headers, IDs and existing Relationship frames, revisions, query and maintenance behavior. A pre-feature REL starts with no synthesized Observations. New relational Observations are written once and read through the Observation surface. Existing manual/imported Relationships remain available to their existing consumers and to candidate selection. Their existing Memory-level references carry their original availability semantics. In particular, historical records need no invented citation spans and new inferred Relationships do not feed automatic Entity identity as independent evidence.

Validate new records at their physical publication prefix. Version the private checkpoint and restore the Observation/progress projection on exact reopen. Use the same physical-prefix checks when replaying a new carrier after a verified checkpoint. Unhandled or incompatible checkpoint state falls back to verified ordinary replay. Include the domain in historical proofs. Verified same-owner copies and supported reclamation preserve these carriers. Pruned evidence resolves as unavailable from history. Refuse any unsupported rewrite, divergent reconciliation or prune that would discard a required Observation carrier or evidence proof before creating a destination. Readers predating the new native carrier may reject files after the first audit publication. Document the minimum version that can read those files.
