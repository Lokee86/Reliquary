# Perception in Hermes and Mercury

Parent index: [Planning](./INDEX.md)

## Purpose

Enable the released same-REL Perception lifecycle and chat recall in the Hermes directory plugin and Mercury’s built-in Reliquary integration. Each host needs to start the existing Core worker on its authorized writable RELs, supply the tested native Jev route, and return current Observations with trustworthy source references.

## Overview

Core `v0.1.0` at `896c6768` already owns audit scheduling, Observation publication, reconsideration, standing, and history. Hermes plugin `main` at `a9cfd3a` vendors Core `33f32b2d`. Mercury `main` at `2306a172` uses Core `f212204d`, which forked before Perception and adds hosted Switchboard and Archive/Echo APIs. Both hosts currently project chat recall as Memories. Deliver one compatible Core revision, then integrate and verify each host using its own release path. ## Compatibility and rollout

Build and test in separate checkouts, build targets and profiles. Keep the active processing session’s pinned executable, configuration, owner files and working directories outside the integration. A pre-Perception REL opens on the new reader with its existing headers, owner ID and history. The first Observation publication makes that REL require an Observation-capable reader. Prove open, publication and restart on a copy before any profile upgrade. Coordinate a production cutover after its processing is quiescent. Keep a verified pre-upgrade copy if a return to the previous reader is needed.

Prepare an updated Hermes package and exact catalog candidate using the existing bundling and attestation flow. Stock catalog adoption follows a reviewed upstream pin. Mercury ships through its own Desktop and Gateway build process. Maintainer approval and adoption are separate from the implementation acceptance gates.
