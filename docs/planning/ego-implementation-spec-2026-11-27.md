# Ego specification and implementation plan

Parent index [Planning](./INDEX.md)

## Purpose

Give Hermes and Mercury the same Reliquary-owned Identity, Pinned context and verified summaries. A normal installed profile can build the package from its active PHY and authorized RELs, refresh it as Memories change, and inspect the saved records and provenance. The current REL audit returns Ego topics, but the worker keeps the latest list in memory and has no consumer that can resume or publish it. Existing Ego records provide Identity and Anchor storage and a singleton synthesis projection. [Current handoff](../../crates/reliquary-runtime-gateway/src/instance_perception/poll.rs) · [Existing record model](../../crates/reliquary-ego-store/src/model.rs)

## Overview

Deliver Ego as one integrated feature. Start with managed audit capture and durable owner publication. Build the tested REL synthesis sequence and incremental PHY summary on those foundations. Give both hosts the same read-only selection policy and give authorized users direct control through the Inspector. Each useful implementation slice has a focused exit condition below.

## Ownership and interfaces

| Owner | Responsibility |
| --- | --- |
| Memory Web audit | Bounded pages, graph and lexical exploration, exact source slots and independent list coverage. REL uses the shared Ego and Perception discovery request. PHY runs the Ego list over its own evidence. |
| Ego | Topic consolidation, synthesis and verification policy, summary revisions and eligibility decisions, Pin ranking, and selection of a budgeted package from authorized values. |
| Application and Gateway | Application composes source capture, configured inference, the pending-work database and publication. Gateway binds the explicit active PHY, REL scope, owner-specific grants, mounts and worker leases. Root exposes owner-scoped operations and the package to hosts. |
| Owner-session and Ego Store | Owner-session serializes reads and commits on the mounted authority. Ego Store validates and replays Identity, Anchor and summary records in the owning file. |
| Switchboard | Configured structured General and embedding routes, route binding and the bounded tokenizer-tool job used for PHY compression. |
| Context Engine and host adapters | Calculate available tokens and place the Ego package in the outgoing request. Context Engine owns current-chat and cross-chat policy. Hermes and Mercury map the shared package onto their own request builders and keep transcript authority. |

Use existing crates and the shared Root boundary. Bind ordinary synthesis and verification to the profile's configured structured General endpoint and comparisons to its accepted embedding profile. Hold work when its required route is unavailable. Pass immutable captured values and exact references into the semantic stages. Use one authorized package operation that accepts the active owner bindings, turn query and budget, and returns separate Identity and standing-context blocks, their measured token cost and the source/revision bindings. Recheck the bindings at handoff. Host adapters consume those blocks and use the existing profile lifecycle and approval surfaces. ## Audit and recovery

- **REL.** Reuse the combined topic-and-proposal contract and existing v1 audit progress. Freeze the initial eligible cut and finish it in batches of at most 125 Memories, within the route budget. Continue from the saved page between polls. Run the regular audit after each 25 newly settled Memories and revisit changed sources and graph endpoints. Keep 15 Stale and five Dormant samples for Perception, including its existing receptor routing. Ego reads Fresh sources. Reawakened sources can enter the next scheduled audit. Let both lists follow eligible graph links from a supplied slot using the same bounded optional evidence allowance as lexical search. Validate permission, cut and list eligibility on every hop. [Audit contract](memory-web-audit-spec-2026-11-24.md)
- **PHY.** Cover the initial eligible active, settled PHY web using the same bounded audit machinery, then refresh after five eligible Memory changes. All types and categories can supply evidence. Add explicit active-settled PHY eligibility to the shared auditor and retain the REL Fresh filter for REL evidence. Read the existing Memory change and Dream settlement streams through a PHY capture API. Admit retained revisions that already carry accepted PHY import authority through that existing route. Count completed first settlements and effective revisions or eligibility changes once, including removal of previously eligible support. Coalesce repeated updates to the same source within a capture. Bind pages and the accepted frontier to the owner history generation. Use Chronos and source timestamps for scope and effective timing. [PHY summary design](roadmap.md#phy-summary) · [Settlement stream](../../crates/reliquary-owner-session/src/records/dream_settlement.rs)
- **Bind the destination explicitly.** Trusted profile admission supplies the active PHY and its write authority through the existing writable PHY mount and `OperatePhylactery` grant. Authorize the source REL independently. Scope each work item to destination PHY, source owner and history generation, logical run cut, capture digest, batch ordinal and contract/route binding. Multiple eligible profiles can receive the same REL discovery result only after independent source and destination authorization. Perception's REL lease and progress remain owner-local. [Product grants](../../src/host.rs) · [Owner workers](../../crates/reliquary-runtime-gateway/src/owner_workers.rs)
- **Persist before acknowledgment.** Save each accepted Ego batch, including empty accepted batches, as owner-bound pending work in a local SQLite transaction. Keep references and stage receipts sufficient to resume from the captured cut. Acknowledge the Ego list only after the relevant handoffs are durable. Preserve accepted Perception results and continue its independent work when Ego persistence or synthesis is pending. Replay insertion by stable batch ID. Finalize the covered summary cut only after its required batches have accepted or been excluded under the current source policy. Retain receipts until that cut and completion marker commit to the PHY and the audit cursor can no longer replay their batches. On restart reconcile against the durable completion marker before retrying inference or publication. [Handoff design](roadmap.md#ego-audit-handoff-and-recovery)
- **Catch up on upgrade.** A v1 REL page accepted before durable Ego handoff may have lost its topics. Start one separate bounded Ego bootstrap for the new destination/source pair using the same eligible-source reader and discovery contract, with its own pending cursor. Preserve accepted Perception coverage and contributions. Coalesce overlapping Ego work by exact source revision and cut before synthesis. Join subsequent shared batches when both features have work. Capture newly committed changes for a later cut.

Run from normal managed processing. Hold inference outside writer locks. Recheck route, mount, history generation, grants, expected summary revision and exact cited source standing before publication. A stale or incomplete attempt resumes from the current authorized evidence; an accepted empty result records completion. Delay transient provider retries using the existing backoff. Keep private source text out of logs and use the profile's protected local data directory for pending work.

## REL summaries

For each source REL, publish an itemized summary in the active PHY. Use the frozen **Audit → Consolidate and compare → Synthesize → Verify → Publish** contract. Embed topic text, combine duplicate topics at 0.85 similarity and union distinct references. Compare with the stored section and skip synthesis when it has no new exact Memory revisions. Make one structured synthesis call for up to five cited points, then one structured verification call for the exact points and source packet. Accept each point independently after exact quote binding and the meaning, status, time and attribution judgments. Keep qualified wording and supported dates. [Frozen REL contract and prompts](ego-rel-summary-spec-2026-11-26.md)

- A verified point from a refresh cites at least one new source revision. Match potential live replacements in its section by compatible point vectors first, then shared owner-qualified Memory IDs if there is no usable vector target. A unique match requires evidence that the new statement updates the same subject and applicability. When the match requires judgment, send the exact candidate predecessor and its supporting passages alongside the existing Verify request. Bind the replacement judgment to its ID and revision. Retain the four tested point checks and their acceptance rules. Use the same Verify call for this judgment. Independently valid different scopes become separate points. Hold an ambiguous replacement and keep the existing point. A later evidence change can revisit the match.
- Publish additions, replacements and tombstones in one owner commit. Replacement advances the same point ID. Preserve unaffected points, their provenance and retained revisions. Plain tombstones permit later proposals. An opt-in suppression flag compares the retained text, scope and compatible vector with future candidates locally. Only a duplicate in the same applicability is blocked. Lifting the flag is an append. [Point history and suppression](ego-rel-summary-spec-2026-11-26.md#durable-summary-records)
- For current context, first check authorization and exact source standing. Project Freshness from each source REL without reinforcement. Calculate each point's arithmetic mean over all distinct supporting Memories. For Freshness eligibility, omit the point only when that mean falls below the Fresh band. Count its distinct Stale and Dormant supporting Memories for budget priority. This is reversible serving eligibility. Recheck it during context selection and keep the original revisions for inspection. [Derived point Freshness](https://github.com/Lokee86/Reliquary/blob/2b5bd0ea/docs/ego-web-synthesis-plan.md#L101-L114)

## PHY summary

Maintain one verified text revision in the active PHY. Use the audited evidence for the initial summary. For a refresh, pass the previous verified text and its exact provenance, the audited changes since its accepted cut and the original passages needed to check affected claims. Preserve current standing guidance and narrower exceptions. Use the stored provenance to identify evidence affected by corrections and withdrawals, and reopen original passages for new or substantively rewritten claims. If the mandatory evidence packet exceeds the route limit, analyze it in bounded packets and carry supported content with exact references into the draft. Mark coverage after the captured input is processed. [Incremental input contract](roadmap.md#phy-summary)

1. Synthesize a full replacement text and bind its material content to captured evidence. Write the text in independently meaningful paragraphs, with conditions and dates together with the claims they qualify. Put the most broadly useful current preferences and standing guidance first so a short routine profile can use the start of the same summary.
2. Count the exact text using the fixed counter for the saved cap. Start with a **4,000-token** cap. If the draft exceeds the cap, run one bounded compression job with a local tokenizer tool using the same counter. Allow up to four tokenizer results and one terminal candidate per job. A continuation belongs to the same bounded job. Reuse Switchboard transport and add only the tool continuation it needs. Preserve distinct information, supported dates, scope and exceptions. Treat exhaustion without a fitting candidate as a held refresh.
3. Verify the exact final text in a separate structured request. For each final paragraph, bind cited slots and quotes to exact source ranges and check meaning, time, scope and attribution. A byte-identical paragraph can carry forward its verified binding after checking current source standing. If compressed, give Verify the draft and check for material loss or changed meaning. A hold on required content holds the replacement as a whole. Check the final cap and evidence again at commit, then append the complete text and its provenance under one revision. Keep the preceding revision available when it remains valid. Current context requires current support for the saved text.

Persist exact provenance ranges against the text without creating a second set of durable PHY topics or points. Both routine injection and authorized on-demand PHY summary recall use this revision. Original PHY Memories remain searchable. [Provenance model](ego-rel-summary-spec-2026-11-26.md#durable-summary-records) · [Token-counting seam](../../crates/reliquary-context-engine/src/compaction_budget.rs)

## Inspector and assistant controls

Extend the existing Reliquary dashboard Inspector and its authorized write admission in Hermes. Use the same Root operations for native host controls. Give participating profiles explicit owner-scoped write admission for their active PHY. Ordinary chat recall retains its existing grants. [Inspector capability boundary](https://github.com/Lokee86/reliquary-hermes/blob/main/docs/local-service.md)

- **Identity.** Reuse existing PHY-owned Identity revisions and append a separate active-selection record. Let authorized Inspector users create, edit and switch Identities. `/identity` prepares a draft. Save only after user approval bound to the exact text, PHY, Identity ID and expected revision. Recheck owner and revision on approval. Retain the host Identity when there is no eligible active Ego Identity.
- **Pinned context.** Use one scoped lookup for the Inspector and assistant, including Pins omitted from the prompt. Expose owner and High, Normal or Low priority. New Pins default to Normal. `pin_anchor`, `modify_anchor` and `delete_anchor` require explicit PHY or REL scope, with current revision checks for edits and removal. On a clear user reaffirmation or softening of the same standing instruction, allow a priority-only edit in the normal tool path. Move one tier in the appropriate direction or use the tier explicitly named by the user. Persist the new priority and preserve the text. Writes append revisions or tombstones and recheck grants at use.
- **Summaries.** Give authorized users current and retained revisions with exact source links. Support point replacement, removal, optional suppression and lifting suppression through the same expected-revision write boundary. Inspection projects current eligibility without awarding Freshness. [Controls design](roadmap.md#ego-summary-inspection-and-control) · [Existing owner storage](../../crates/reliquary-ego-store/src/store.rs)

## Shared budget and host assembly

Context Engine supplies the lesser of actual remaining input room and the initial ceiling of about **20% of usable model input**, after the applicable output reservation. Use the destination model's token counter or conservative bound from its host. Account for final block wrappers and separators. Ego fits Identity, Pins, the routine PHY profile and REL points in that order. Context Engine may use what remains for recent cross-chat context when that feature is available. Current-chat transcript and compaction are budgeted separately. [Budget design](https://github.com/Lokee86/Reliquary/blob/2b5bd0ea/docs/ego-cross-chat-context-plan.md#L51-L69)

| Layer | Packing rule |
| --- | --- |
| Identity | Use the whole active approved Identity. Keep the host's ordinary Identity path when the Ego block is unavailable or cannot fit safely. |
| Pins | Rank applicable authorized Pins High → Normal → Low. Within a tier prefer active REL → PHY → parents → farther ancestors, nearer first. Break exact ties by owner ID and Pin ID. Pack complete Pins in order and skip a Pin that cannot fit. |
| PHY profile | Try the full verified text. When it cannot fit, use its longest complete leading paragraph sequence that fits. The most useful general guidance is written first during synthesis. |
| REL points | Find a bounded set of relevant eligible points using existing lexical scoring on the turn query. Include vector matches when a compatible query vector is already available. Use the existing candidate limit and stable IDs. Give points with fewer Stale or Dormant supporting Memories higher inclusion priority. On equal counts, prefer the active REL, then nearer authorized ancestors, higher mean source Freshness, stronger turn match, and ascending owner, topic and point IDs. If the points exceed the remaining budget, remove whole points from the lowest-priority end of that order until they fit. Keep qualifiers and attribution together. |

Use the active REL and authorized ancestors from the existing dependency closure. Application supplies authorized point matches and current source Freshness to Ego's selector. Pass the budget and counter identity over the existing Hermes native IPC. Mercury supplies its counter in process. Expose Identity and approved standing Pins in the appropriate host blocks. Render derived summaries as sourced informational context. Keep the package selection read-only, including when switching profiles, resolving a missed source or assembling a new request. Recheck current grants and source standing before disclosure.

- **Hermes.** Update the bundled Core. Use the stock profile-selected Context Engine hook. Calculate remaining input from the assembled request and model limits. Match and replace the exact rendered leading `SOUL.md` block and insert the rest once. Keep the rendered host Identity if there is no active Ego Identity. Use the original request on a mismatching identity block. A participating profile disables `memory.memory_enabled` and `memory.user_profile_enabled` and retains the Reliquary memory provider. Use the tested stock seam with the documented version. [Hermes design](roadmap.md#ego-package-in-hermes)
- **Mercury.** Update the native Core pin and native Reliquary integration. Use Mercury's persona slot to render the approved Identity, with its normal `SOUL.md` fallback. Insert the rest once. Native Reliquary provider selection disables the built-in notes layers. Preserve existing Memory, Archive, Echo and recall APIs, native compaction and transcript ownership. [Mercury design](roadmap.md#ego-package-in-mercury)

## Storage compatibility and rollout

Keep the existing REL and PHY 2.1 headers and owner IDs. Use versioned Ego records in the current append sequence, with expected revisions and accepted work IDs. Decode existing Identity, Anchor, Personality and singleton synthesis records for their retained 2.1 history. The new package reads the approved Identity, Pins and verified summary revisions. The earlier Personality projection remains historical. Include new record variants in ordinary replay, historical proofs and verified same-owner copies, and in checkpoint suffix replay where the owner uses checkpoints. Operations that discard or rewrite referenced history must preserve the new proofs or refuse before creating the destination. [Owner replay and maintenance](../architecture/owner-session.md)

Ship reader and writer support in the same release before enabling writes. A build without the new Ego codec may reject an owner after it receives a new record. Readers continue to open existing 2.1 files. Use the stable Root product APIs for existing uses and switch opted-in Ego consumers directly to the shared package. Keep work in feature branches until the Core and both host gates pass, then roll the compatible Core and adapters into their normal release paths. Existing host availability and deployment schedules are external to the acceptance gate.

## Implementation sequence

| Step | Depends on | Exit condition |
| --- | --- | --- |
| **1. Owner records and product boundaries** | Current 2.1 readers | Versioned summary records, active Identity selection, authorized Pin lookup/edit and expected-revision gates round trip through Owner Session. Controlled 2.1 compatibility and maintenance behavior are defined. |
| **2. Audit, capture and pending work** | Existing audit and owner capture | Graph follow-up, independent list acknowledgment, upgrade catch-up and durable REL and PHY work flow from normal managed mounts. Reopen keeps the accepted cut and pending batches. |
| **3. REL workflow** | 1, 2 | Existing structured routes produce independently verified points, update the correct live ID, retain unaffected points and commit the new cut exactly once. |
| **4. PHY workflow** | 1, 2 | Initial and five-change refreshes use the same durable handoff, with whole-text verification, conditional tokenizer-assisted compression and atomic replacement. |
| **5. Shared package and controls** | 1, 3, 4 | Root provides scoped controls and a deterministic, token-checked package. The Inspector can inspect provenance and edit Identity, Pins and summary controls. |
| **6. Hermes and Mercury** | 5 | Both adapters consume the same Core output, expose the authorized assistant tools and Identity approval flow and capture a correct ordinary outgoing request over a disposable profile. |
| **7. Integration** | 1–6 | Check the canonical live path and retained external interfaces, document behavior and ship the complete feature after the focused gates. |

Steps 1 and 2 can proceed in parallel after agreeing on the owner, cut and work ID contracts. Steps 3 and 4 can proceed independently once those foundations are integrated. Host work can prepare against the agreed package interface and merge once the Core gate passes.

## Notes

This release covers summary generation, retained history, scoped controls and routine Ego injection. Cross-chat selection, full transcript ownership changes, cross-owner summary synthesis, automatic writes triggered only by Freshness, and a separate Personality layer are outside this release. Work against disposable owners and isolated profiles so ongoing processing stays independent.
