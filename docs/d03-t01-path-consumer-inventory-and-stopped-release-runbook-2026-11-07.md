**Status: DRAFT / INCOMPLETE.** This is a repository-only consumer inventory and a proposed runbook. ## Scope and decision

Inspected product source from the post-G4 product integration base 26e84f45, the D03 synthetic-only staging branch, and the repository's public acceptance artifacts. Synthetic files are excluded from claims about production product selection. No private corpus or deployment host was accessed.

The inspected product does **not** expose one central generation-selection binding. Public opens, Gateway mounts, the host's remembered owner paths, and CLI commands take explicit paths. The host records per-owner paths only in an in-memory map. The repo scan found no production launch/service configuration or shared owner-path selector.

Therefore, do not select or invent a universal manifest selector on the evidence available. If the complete external deployment inventory confirms that consumers remain explicit-path users, use a **stopped-release path-update** procedure: stop and quiesce every writer and launcher, update every verified mapping while the release is stopped, and keep all writers disabled until all required paths and owners pass read-only validation. A central manifest selector is a possible future architecture change only after every relevant consumer has adopted it. Neither route may be treated as an atomic multi-file transaction.

## Proposed pre-write rollback runbook (future authorized operation only)

This is a draft for review, not an instruction to activate now. Do not access an authentic corpus or change live paths under this task.

**Before the stop**
- Require the approved D02-T04 report and digest, G5 ReleaseReady, an exact operator authorization, the validated candidate manifest digest, the exact prior-generation mapping, and verified immutable rollback assets.
- Print/review a per-consumer path table covering every deployment configuration and direct library host. Record expected owner IDs/kinds/scopes, runtime artifact hashes, per-file hashes, sidecar/receipt digests, and the path/config backup locations.
- Confirm the candidate and rollback bundle are separate and immutable. No candidate may be selected while validation is incomplete. Before each later routing update, persist a durable step record containing phase, previous/candidate generation IDs, manifest digest, original and intended complete path maps, next mapping step, and write-boundary state. If that record cannot be durably written, make no routing change. On restart, before any consumer starts, read the record and inspect every current path mapping. If the observed map is a known partial step matching the record, under the stopped fence and recorded authorization complete the remaining updates or restore the prior complete map, then verify every path; do not serve a partial map. If intent or actual mapping is unknown or mismatched, remain stopped/Held.

**Stop and fence**
- Fence new opens and stop all active owner-path consumers, including already-running readers, runtime hosts, CLI jobs, maintenance tools, and writers. Drain accepted work or durably hold it, close writer leases, drop caller-held Rel/Phylactery/session handles, and verify processes have exited or prove an explicit safe hold. Gateway quiesce removes a mount but does not prove that caller-owned reader objects or other processes have closed their handles. Do not update routing while an old reader can still serve data.
- Preserve queue, stream, host-operation, and receipt state. Record each queue state_dir, journal, and lock separately from owner-generation paths; close queue handles to release locks and do not call the mutating queue-open API during read-only health checks. Unknown external outcomes remain Held; do not redispatch them because a path changed.
- If any process, write lease, owner mapping, or operation outcome is unknown, abort while keeping writers disabled.

**Update and read-only validate**
- With all launchers, active readers, and writers stopped and old handles closed (or an explicitly proved safe hold), update each explicitly inventoried owner path to the exact candidate generation. Persist the intended step and manifest digest before each individual update. This is a coordinated stopped window, not an atomic transaction. If an update fails, remain stopped/Held and reconcile only the mappings recorded in the durable transition record. If an unexpected consumer appears, remain stopped/Held, inventory its identity and actual paths/configuration, and restore only mapping entries present in the durable record; never invent an original mapping. Do not restart consumers until every required mapping is known and consistent.
- Start only the authorized current-only runtime in an isolated read-only validation mode, not serving product traffic. Open each required owner separately through current owner admission, then compare actual owner ID/kind/scope and file digest with the same validated manifest. Verify pairings, runtime hashes, semantic/history proofs, sidecars, and operational receipts. Do not use Instance::open_conversation_queue for this check because it creates/opens the writable journal and lock. No partially validated owner set may serve traffic.
- Run only bounded, approved read-only health checks, then close all validation readers. Re-hash every candidate owner file, runtime artifact, and required operational sidecar after the tests; compare against the same manifest digest and fail closed on any change. Keep writers disabled until a separate G5-authorized writable transition is explicitly recorded.

**Rollback decision and write boundary**
- Before the first accepted write to the candidate, a failed validation may roll back by stopping candidate readers, closing all candidate handles, restoring the saved previous path/configuration for every consumer under the stopped-release fence, verifying the previous runtime/data hashes, and reopening the previous generation read-only. Persist each rollback step and manifest identity before changing a mapping; after restart, inspect state and reconcile before any consumer starts. Preserve the failed candidate and its evidence for diagnosis; do not mutate or delete it.
- Record the exact first accepted candidate write and receipt as a durable boundary. If that boundary has been crossed, **do not blindly switch to old data**. Stop producers, preserve both generations and all receipts, and choose a separately verified forward-recovery or owner-bound reconciliation/export plan. Do not claim automatic or lossless downgrade.
- Every stop, update, check, failure, mapping restore, and first-write boundary must be recorded against the manifest digest. If evidence is incomplete, remain stopped/Held.
