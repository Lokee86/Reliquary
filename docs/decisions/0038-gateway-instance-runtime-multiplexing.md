# ADR 0038: Gateway and instance runtime multiplexing

Parent index: [Architectural decisions](INDEX.md)
Implementation plan: [Multiplexing implementation plan](../multiplexing-implementation-plan.md)
Baseline evidence: [Multiplexing Phase 0 baseline](../multiplexing-phase0-baseline.md)

## Status

Accepted architectural direction — 2026-10-02; **not approved for implementation** until [Phase 0B readiness gates](../multiplexing-readiness-review.md) are satisfied. Conversation-attachment semantics, multi-principal processing, reliable update publication, authorization and lifecycle fencing need more than the current preliminary roadmap. The user-facing concurrent-submission policy is selected below; its durable queue and execution state-machine mechanics remain a Phase 0B gate.

This amends [ADR 0037](0037-reliquary-context-memory-project-environment.md): Reliquary still owns the complete environment, but its single active REL, single PHY, and managed-session selection move from the shared host to operating-instance context. It clarifies [ADR 0034](0034-cross-owner-relationship-graph-and-active-phy-privacy.md): "active PHY" means the requesting instance's authorized active PHY, never whichever PHY another instance most recently activated. The underlying privacy rule remains unchanged.

## Context

The existing ReliquaryRuntimeHost already mounts several REL owner executions, each with independent runtime and workers. It nonetheless has one host-global active REL, one PHY slot, active-REL-dependent worker switches, and one managed session per REL execution. That makes it unsuitable for concurrent operating instances, including different principals in the same REL or one principal using several devices/agents.

RELs own conversations, streaming checkpoints, durable turns, branches, and Archive activity. PHYs have no conversations and own personal semantic state. A shared REL may be accessed by multiple authorized instances, including instances with distinct PHYs. A PHY may also be attached to multiple instances without becoming multiply owned or multiplying its personal processing.

## Decision

### Two runtime lifetimes

- **GatewayRuntime** is the single long-lived authoritative runtime for a mounted resource set. It owns keyed REL and PHY executions, durable-owner handles, shared background processing, routing and coordination, operation/subscription registries, authorization enforcement, and lifecycle/quiescence. There is one live authoritative execution per durable REL or PHY owner ID.
- **InstanceRuntime** is an attached, independently disposable operating context issued and tracked by GatewayRuntime. It has one authenticated principal/attached PHY, one currently active REL, its own selection of a managed conversation for each REL it uses, and its own live-subscription state. A separate instance can use the same PHY and REL without inheriting its active selection.
- An instance is not a storage owner, not an authority for accessing an arbitrary owner ID, and not a new semantic database. Dropping an instance revokes its subscriptions and its own transient context; it cannot unmount shared RELs/PHYs, kill unrelated operations, or finalize another instance's activity.
- REL dependency topology and context-composition policy remain Reliquary-owned. Normal ambient context is the requesting instance's active REL dependency closure intersected with its grants, plus its own authorized PHY where the capability permits. An explicit owner-qualified API must also authorize the requested owner; "mounted" alone no longer implies permitted. User-private PHY state must never enter REL-wide broadcasts or another principal's context.

The host application authenticates or otherwise supplies a trusted principal binding; the gateway validates/retains that binding and applies its explicit owner grants at every attached operation and subscription. Clients cannot choose or forge another principal by passing arbitrary PHY IDs. Remote transport authentication is a later adapter concern, not a second semantic owner.

### Separate REL state updates from active conversation streams

- Every **connected authorized instance accessing a REL** receives its REL-wide update feed. Committed conversation messages, branch/head and metadata changes, relevant owner mutations, operation statuses and indexing/retrieval invalidation are broadcast regardless of which conversation that instance currently displays. Inactive conversations are therefore kept discoverable and fresh.
- **Streaming output** is delivered only to active subscribers of the relevant authorized REL conversation/generation. Activating an existing conversation attaches to its ongoing stream if it has one. Merely accessing the REL never subscribes an instance to every generation.
- Existing durability ordering is preserved: assistant output cannot be presented as a committed/streaming checkpoint before that checkpoint has synchronized successfully. Transient delivery state and client-side caches are never Archive authority.
- Each REL update feed has a mount-epoch identity and ordered ephemeral event cursor. An instance joining or detecting a gap uses an atomic subscribe-and-snapshot/watermark handshake. After a gateway restart or irrecoverable gap it reconciles authoritative REL state rather than assuming transient event replay. Conversation stream activation similarly returns durable checkpoint/current operation state and a stream cursor before subsequent deltas, deduplicated by operation and sequence.
- **Reconnection resynchronization is mandatory for disconnected instances and RELs**, not just gateway restarts. A rejoining instance must reauthenticate/revalidate principal and owner grants, reacquire its authorized REL snapshot, current branch/conversation state, provisional queue/cancellation status and live-operation status, then reattach only its selected authorized conversation streams. An instance's previous cursor is an optimization, never authority; if epoch/cursor continuity cannot be proven, take an authoritative snapshot plus watermark and resume from that point atomically so a mutation during reconnection cannot disappear. Do not replay another principal's private PHY state.
- When a REL is disconnected, unmounted and remounted, or otherwise loses feed continuity, the gateway must reopen/reconcile its authoritative durable state and owner revision, assign/advance the mount epoch as appropriate, invalidate stale instance caches and restore authorized REL feeds; reconcile host-owned pending/in-flight work and native queue cancellations before redispatch. Distinguish REL/instance network reconnection from explicit revocation or a genuinely absent owner. Disconnection alone cannot cancel another instance's generation or finalize another's session.
- Revocation and instance detach terminate only that instance's feeds. Bounded queues must report overflow/resynchronization instead of silently presenting stale state.

### Safe conversation writes and operation lifetimes

A REL conversation/branch has one gateway-coordinated write/operation authority and accepts every authorized submission with its expected parent/revision and submission identity. The gateway establishes a final order for pending submissions and never silently overwrites an accepted message. It also owns generation operation identity, live fan-out, checkpoint acknowledgment, cancellation authorization, terminal result and recovery visibility. Reading/subscribing to a generation does not grant permission to cancel it.

**Default: sequential queue.** Two instances submitting to the same conversation behave like a single user entering messages sequentially: enqueue both as provisional state, process pending submissions chronologically on the same branch, and add each to durable conversation history only upon its own final submission, preserving the chosen final order. For genuinely simultaneous submissions, randomly choose their relative order once, then retain that order permanently. Only submissions still pending may be reordered by timestamp: never rewrite already committed ancestry when an older, delayed submission arrives. Use gateway-verified timestamps/order metadata rather than trusting unsynchronized client clocks; exact timestamp trust and near-simultaneous admission boundaries are Phase 0B details. When a generation is already executing against a context snapshot, enqueue additional submissions for the next safe continuation rather than silently altering that in-flight context. Broadcast provisional queue-state changes to connected authorized instances accessing the REL; broadcast a committed-message update only after finalization, and send live generation output only to active conversation subscribers. **Queued submissions are provisional, independently cancellable state and are never Archive conversation-history turns.** Accepting/enqueuing sends a provisional status notification, not a completed message or semantic mutation. A queued submission remains cancellable by its authorized submitter until the gateway atomically transitions it into final Archive submission; successful cancellation removes it from the queue and sends a queue-status update, without adding a conversation turn, Archive activity, Episode, Insomnia work or branch. If a cancellation races finalization, the gateway serializes them and reports the winning result: cancellation wins with no turn, or finalization wins and the submission becomes ordinary history (subsequent cancellation is a distinct committed-operation policy). **The provisional queue must survive gateway restarts.** Persist each Reliquary-admitted native pending submission, stable submission ID, authorized submitting principal, target REL/conversation and ordering metadata in a gateway-owned pending-submission journal separate from Archive conversation history; acknowledge enqueue only after the pending record is durable. Persist cancellation so cancelled entries cannot reappear. On restart, reconstruct the pending queue in its established order. Finalization must be idempotent across journal and Archive: commit under the stable submission ID, then mark the queue entry finalized; if the gateway crashes between these steps, recovery checks the Archive before replaying the entry and must not duplicate it. Queued records must never count as Archive turns, activity, Episodes or Insomnia inputs. Define the precise journal storage, replay and finalization-fencing mechanics in Phase 0B without introducing a general cross-file transaction framework.

**Selectable alternative: automatic branching.** When concurrent submissions genuinely conflict on the same branch head, preserve both on distinct branches with explicit branch identities, understandable UI labels/notifications and clear per-instance branch selection. Do not silently move another instance to a branch. Normal sequential submissions need not fork. The effective conversation-level policy must be gateway-coordinated so simultaneously attached instances cannot apply contradictory policies; persistence/inheritance of this preference is a Phase 0B detail.

Live synchronization is mandatory for both policies. The basic writer-admission and queue/branch state machine is a Phase 1 prerequisite, not an optional future conflict-handling extension. Archive-local ancestry, idempotent submission and durable recovery remain authoritative.

### Native machinery and selective host integration

Reliquary must provide its own queue, session/operation coordination, cancellation, recovery and update mechanisms wherever its independent operation or correctness requires them. **Host integration is selective, not host-first delegation:** inspect the host's actual capabilities and delegate an overlapping responsibility when running both would conflict and the host can satisfy Reliquary's required contract. Do not surrender an internal capability merely because the host implements a superficially similar feature. When delegation would compromise Reliquary, retain its native machinery; parallel host and Reliquary mechanisms are acceptable when they have distinct scopes or explicit handoff/reconciliation.

Apply this assessment **per responsibility**, rather than selecting a global native/delegated mode. **Preventing cancelled work from executing is the primary queue-integration objective. Prefer the host's queue for host-executed work whenever it supplies effective pending-item cancellation, status/reconciliation and an atomic dequeue-or-cancel boundary.** A cancelled submission must not subsequently cross into execution because Reliquary independently retained or replayed an older copy. If a host already provides compatible scheduling/admission/cancellation for the overlapping stage, use that interface instead of introducing a competing scheduler. Where native internal work or Reliquary correctness requires its own queue, keep it; separate upstream host and downstream Reliquary stages may coexist only with explicit ownership transfer and propagation of cancellation before downstream execution. Warlock is evaluated by its actual queue/cancellation capabilities, not hardcoded to either choice. Reliquary always owns its Archive commitment, REL/PHY processing authority, provenance and privacy invariants.

For each overlapping capability, document its boundary and authoritative state transitions (who admits work, orders it, may cancel it, dispatches it and declares it completed); never allow two unsynchronized parties to make the **same** transition. Connect distinct stages with stable submission/operation identities, explicit acknowledgments, cancellation propagation, status mapping and replay reconciliation. **Every handoff must recheck cancellation and identify which side now has dispatch authority; dequeue and cancellation must be serialized at the authoritative queue.** No cancelled pending item may be requeued or dispatched after restart or reconnect. A host capability without safe cancellation or status reconciliation must not replace Reliquary's stronger native mechanism; report any unavoidable limitation rather than pretending the guarantee holds. Duplication of machinery is permitted; duplicate **execution or commitment of the same submission** is not. Cancellation of already-running external operations is a separate cooperative-interruption contract: request the host to stop and report whether it actually stopped, without falsely promising to undo completed effects.

**Startup and reconnection:** restore Reliquary's native pending state, then immediately initiate connection to each configured host. The host and Reliquary exchange capabilities and reconcile the state and ownership of shared/in-flight work, including cancellations, before resuming dispatch across their boundary. Give cancellation reconciliation precedence over replay, and never revive previously cancelled pending work. If the host is unreachable, preserve Reliquary's own pending work, expose the degraded connection and retry automatically; unaffected native work continues. Unknown host operation status is reconciled rather than blindly replayed. A host with its own queue may retain that queue; do not require wholesale importing, disabling or duplicating it when separate responsibilities and a safe handoff suffice.

Expose stable submit/status/cancel/subscribe/reconnect contracts at the Reliquary integration boundary without pretending every host supports every operation. Phase 0B must specify the per-capability authority map, handoff/idempotency protocol, reconnect ordering and fallback conditions. Exactly-once external execution is not guaranteed without host cooperation; Reliquary's own final Archive commitment must remain idempotent.

### Shared processing

REL processing is scheduled once per REL execution, not once per attached instance. PHY processing is scheduled once per PHY execution, not once per REL that happens to be active. Requests that need personal context capture and authorize their principal/PHY at enqueue or execution rather than reading a mutable host-global "active PHY". REL-owned output must not inadvertently incorporate one user's private PHY material.

Multi-owner operations must preserve independent owner-lock lifetimes and deterministic fan-out. Current per-REL interaction locking is acceptable until measured contention justifies splitting it.

### Compatibility and migration

Preserve current REL/PHY file kinds, durable owner IDs, Archive conversation and provenance semantics, Memory/Entity/Observation/Graph ownership, Project Environment/Lore authority, and existing provider endpoint traits. The gateway/instance split is initially in-process and is designed for an eventual standalone gateway without imposing an RPC protocol now.

This is a **staged internal hard cut**: build the canonical gateway and instance interfaces, migrate consumers directly, and delete the old ambient-host internal API. Preserve documented on-disk compatibility and any independently verified external interface requirement only at the appropriate external edge; do not keep parallel mutable host/instance ownership or permanent forwarding shims.

This work is an independent whole-stack initiative. Ego is an ordinary consumer of instance-relative visibility and does not own multiplexing or change its semantic algorithms here.

## Consequences and verification

- The current global active_key, single PHY slot, active-PHY-dependent per-REL worker toggles, and OwnerExecution-managed session singleton cannot remain operational sources of truth.
- REL and PHY registries must enforce unique authoritative live owner executions, coordinated mutation, quiescence and independent shutdown.
- An instance's active REL/PHY affects no other instance; principal attribution follows its verified identity.
- REL-wide updates reach all appropriate connected instances; only active conversation subscribers receive live stream events; stale and reconnecting instances reconcile without races.
- Multi-client concurrency tests must cover same/different PHY, same/different REL, same conversation, source attribution, branch conflicts, slow subscribers, reconnect, revocation, worker deduplication, and shutdown.
- Architecture documentation must be updated as each phase ships. Until then this ADR is target architecture, not a claim about current APIs.

## Alternatives

- **Exclusive PHY checkout:** rejected as the general rule; it would unnecessarily prohibit one user across desktop/phone and independent agents. A single authoritative PHY execution provides consistency without exclusive client attachment.
- **Per-instance copy of REL or PHY execution:** rejected; duplicates mutable authority, background processing, indexes and conflict handling.
- **Send every generation to everyone accessing a REL:** rejected; stream delivery is conversation-subscription-scoped even though general REL updates are broadcast broadly.
- **Make Ego or Warlock the multiplexing owner:** rejected; this is Reliquary-wide execution machinery, while applications remain hosts and semantic subsystems remain consumers.
